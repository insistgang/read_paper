## 摘要

**英文原文（据 PDF 提取文本整理）**：

> Botnets, which consist of thousands of compromised machines, can cause significant threats to other systems by launching Distributed Denial of Service (DDoS) attacks, keylogging, and backdoors. In response to these threats, new effective techniques are needed to detect the presence of botnets. In this paper, we have used an interception technique to monitor Windows Application Programming Interface (API) functions calls made by communication applications and store these calls with their arguments in log files. Our algorithm detects botnets based on monitoring abnormal activity by correlating the changes in log file sizes from different hosts.
>
> **Keywords**: IRC; DDoS; Bots; Botnets; API function calls

## 研究背景与动机

- **为什么要做**：协同攻击近年爆发式增长。攻击者通过 IRC 网络控制被感染的“僵尸”（zombie）机器，对其他系统发起分布式攻击。被感染机器中运行一段名为 bot 的恶意代码，会响应攻击者的各种指令。挂在同一 IRC 频道上的一组被攻陷主机即构成一个僵尸网络（Botnet），可被攻击者通过命令与控制（C&C）远程操纵，执行 DDoS 等恶意活动。当前僵尸网络的常见用途还包括垃圾邮件/邮件炸弹、窃取系统信息、终止程序、向在线企业勒索钱财等。需要新的有效技术来检测它们。
- **之前方法的问题**（引言明确列出）：
    1. **蜜罐（honeypot）的局限**：蜜罐是一种不向合法用户提供任何服务的系统资源；其问题在于——若没有针对它的活动指向它，它就无法检测到可疑流量。
    2. **监控标准 IRC 端口会产生漏报（false negatives）**：因为 bot 可以运行在非标准端口上。
    3. **通信通道缺乏可用于检测的简单特征**：例如外发连接长度各异、每条连接传输的字节数也不固定。
- **核心思路**：作者的目标是——监控若干主机上日志文件大小的行为变化，并找出这些变化之间的相关性，以此检测僵尸网络。其依据是：bot 会同时响应命令，从而在各自的日志文件中产生相同的变化速率。该方法**不**搜索 IRC 流量中的特定模式，因此处理时间更短；也**不**监控标准端口、**不**担心加密流量，因为它监控的是系统行为的变化而非每个数据包的内容。本文只针对集中式（centralized）网络的僵尸网络；P2P 僵尸网络的检测留作未来工作。

## 关键贡献

1.  提出一种**基于 API 函数调用拦截**的数据收集机制：用系统级（system-wide）拦截技术监控当前系统上所有线程，拦截通信应用程序（如 IRC 客户端 mIRC）发起的 socket API 函数调用（`send()`、`sendto()`、`recv()`、`recvfrom()`、`connect()` 等），并将调用及其参数记录到日志文件。
2.  设计并实现一个**日志文件大小记录程序**，每秒记录一次各主机日志文件的大小，持续时间 t，形成时序数据。
3.  提出并实现一个**关联算法（Correlation Algorithm，见 Algorithm 1）**：检测不同主机日志文件大小是否**同步变化**——全部不变（全 0）或全部改变（全 1）均记为“相关”，否则记为“不相关”，据此区分正常与异常行为。
4.  在 **VMWare 搭建的虚拟 IRC 网络**中设计正常/攻击各两种场景的对比实验，验证该方法可区分正常用户行为与僵尸程序（sdbot）的攻击行为。
5.  用 **ROC 分析**评估算法，以日志大小的百分比作为阈值，研究阈值在 0%~100% 范围内变化时的检测率与误报情况（具体数值见“实验”一节，原文表述需谨慎引用）。

## 方法

- **整体框架**：系统由三部分组成——数据收集（DLL 注入与 API 钩子）、数据记录（每秒记录日志文件大小）、数据分析（关联分析器）。
- **输入输出**：
    - **输入**：运行在各主机上的通信应用程序（如 mIRC）所产生的 socket API 调用。
    - **输出**：关联分析结果（相关事件数 vs 不相关事件数），据阈值判断是否存在可疑（僵尸网络）活动。
- **关键模块**：
    1.  **API 拦截 / DLL 注入模块**：实现一个动态链接库（DLL），用拦截函数（如 `myrecv()`）替换目标函数（如 `recv()`），并把该 DLL 注入目标进程（如 mIRC）的地址空间。DLL 一旦载入目标进程，就修改目标进程中目标函数的地址，使其跳转到 DLL 中的替换函数，从而拦截 socket 调用并把调用及参数写入日志。该拦截技术参考了 [5][8]（HookAPI / 进程注入），Detours [4] 等。
    2.  **日志大小记录器**：一个独立程序，每秒记录一次各主机日志文件大小，持续时间 t；t 之后把记录数据交给分析器。**作者假设日志文件受保护、攻击者无法擦除**。
    3.  **关联分析器（Algorithm 1）**：读取各主机数据，比较当前状态（如 t2）与上一状态（如 t1）。某时刻若**所有**日志大小都未变（全 0），或**所有**都变了（全 1），则视为数据“相关”；只要有一部分变、一部分不变，就记为“不相关”。注意：**当前阶段只看“变没变”，不考虑变化的幅度**（量级留作未来工作）。在 outfile 上累计相关值 CV 与不相关值 UCV；若 CV 大于阈值则判定为检测到可疑活动。
- **机制直观解释**：处理僵尸网络时，各 bot 很可能在指定时间内向 bot herder 发送相近数据量，或对外产生相近的攻击流量，从而出现“相关事件”——高相关代表恶意活动，低相关代表正常活动。这种**跨主机的同步性**正是检测信号。
- **训练方式**：文中未提及传统意义上的模型训练；阈值通过 ROC 实验确定。
- **推理流程**：注入 DLL 并启动日志大小记录器 → 收集一段时间 t 的数据 → 关联分析器逐时刻打 0/1 标签、累计 CV/UCV → CV 与阈值比较 → 输出告警。
- **与已有方法的差异**：不分析流量内容、端口或模式，而是关注由底层系统行为（API 调用→日志大小）反映出来的**主机活动同步性**，因此对加密流量与非标准端口具有鲁棒性，处理开销也更低。

## 实验

- **使用的环境**：自建的**小型虚拟 IRC 网络**，跑在一台 VMWare 机器上；宿主机为 Windows XP（P4 2.4GHz 处理器、1GB 内存）。虚拟 IRC 网络含**四台机器**：1 台 Windows XP Pro SP2 作 IRC 服务器，其余 3 台 Windows XP Pro SP2 作 IRC 客户端。每个实验运行 **10 分钟**以收集足量流量。绘图时把 x 轴归一化到 100 字节以便比较（不同图的换算不同，如 100≡275085 字节 / 2754 字节 / 7248 字节 / 4121 字节 / 94050 字节）。
- **对比场景**（正常 2 种 + 攻击 2 种）：
    - **正常场景 1**：3 个用户进行正常对话。
    - **正常场景 2**：3 个用户正常对话并相互传文件。
    - **攻击场景 1**：3 个 bot 加入 IRC 频道，空闲 2 分钟后开始接收 bot herder 的命令（**不含**洪水攻击命令）。
    - **攻击场景 2**：3 个 bot 加入 IRC 频道，空闲 2 分钟后开始接收 herder 的命令（**含**洪水攻击命令）。
    - 攻击场景中三台机器被 **sdbot05b** 感染。
- **评价指标**：相关事件数量（CV/UCV），并用 **ROC 曲线**（横轴累计假阳性率、纵轴累计真阳性率）评估算法。
- **主实验结果**：
    - 仅看单主机日志大小变化（图 1：用户传文件 vs bot 用 UDP/ICMP 洪水），文件传输也会引起日志大小明显增长，**正常与恶意难以区分**；仅看网络统计也不够。
    - 应用关联算法后：3 用户正常对话产生**低相关**（图 2）；即使有用户 3 传大文件导致日志大小突变，仍是**低相关**（图 3）。
    - 攻击场景：bot 接收命令但**未洪水**时数据量虽小，但日志大小变化呈**高相关**（图 4，点状标记代表 bot 间高相关）；bot 接收**洪水**命令时，既有数据量突增、又有高相关（图 5）。
    - 图 6 汇总相关性：正常场景中**不相关事件多**（用户彼此随机响应），但正常场景也出现了**不少相关事件**——作者归因于运行在虚拟机上、虚拟机切换耗时，以及每秒记一次、且实际只有一个人模拟三人，导致正常态产生大量相关事件。攻击场景的不相关事件则源于响应 herder 命令时偶有延迟。

## 局限

1.  **实验环境极小且单一**：仅 4 台虚拟机、单一 bot 样本（**sdbot05b**），且实际只有 1 人模拟 3 个客户端；真实网络的规模、并发与 bot 多样性远超于此。作者自己也指出正常态出现大量相关事件部分源于虚拟机切换与“一人扮三人”的实验设置。
2.  **关键假设强**：方法**假设日志文件受保护、攻击者无法擦除日志**。现实中有权限的 bot 完全可能干扰或删除日志，使方法失效。
3.  **只看“变没变”、不看变化幅度**：当前算法不考虑日志大小变化的量级，作者把“考虑变化幅度”列为未来工作；这也使其对“低相关但确属恶意”或“高相关但实属正常（如虚拟机切换造成）”的情形较敏感。
4.  **检测粒度为群组**：只能检测一组主机的协同活动，无法判定**单台**主机是否被感染。作者把“监控单主机 API 调用数量以检测单个 bot”列为未来工作。
5.  **仅适用于集中式 C&C**：作者明确只针对集中式网络，**P2P 僵尸网络**留作未来工作，而 P2P 是更危险的威胁。
6.  **ROC 评估规模小、表述含混**：阈值附近的误报仅以“1 个 / 2 个假阳性”这种绝对计数描述（样本量极小），ROC 结论的统计意义有限；原文 "zero true negative" 措辞也不严谨。

## 个人评论

1.  **检测思路的启发性**：跳出“分析流量说什么”的框架，转而看“系统在做什么（API 行为）”以及“多主机是否协同（跨主机关联）”。这种基于端点行为 + 内在关联的思路，对后续基于主机的入侵检测、APT/横向移动检测有启发。
2.  **方法简洁但代价是粗糙**：核心算法只判断“各主机日志大小是否同步变化”，无需复杂模型与特征工程，抓住了“命令同步”这一僵尸网络本质——但“只看变没变、不看幅度”也是它最脆弱的地方，正常态的高相关（虚拟机切换、每秒采样、一人扮三人）已经暴露了误报来源。
3.  **实验范式完整但说服力受限**：从问题定义→方法（API 钩子 + 关联算法）→自建虚拟网络验证→ROC 评估，流程完整、是一篇标准的方法论验证型短文；但 4 机 / 单 bot / 一人扮三人的规模，使其更像“概念验证（proof of concept）”而非可推广的结论。
4.  **未来工作指引清晰**：明确点出三条后续路径——考虑变化幅度、监控单主机 API 调用数量以识别单个 bot、扩展到 P2P 网络，为后续研究留下清晰接口。
5.  **对“可信度”的提醒**：本文一些数值（尤其 ROC 那段 "zero true negative"）在提取文本中表述不清，引用时务必回核原图（图 7）与原句，不要把“70% 阈值”直接当成“100% 检测且零误报”的最优工作点。

## 5. 方法详解
- **整体框架**：数据收集（DLL 注入 + API 钩子）→ 数据记录（每秒记日志大小）→ 数据分析（关联分析器）。
- **输入输出**：输入是各主机通信程序产生的 socket API 调用；输出是各时刻 0/1 标签累计而成的 CV/UCV 以及“是否可疑”的判定。
- **关键模块**：
    1.  **DLL 注入 / API 钩子**：DLL 用 `myrecv()` 替换 `recv()`，注入目标进程（mIRC）地址空间，修改目标函数地址使其跳转到 DLL 中的替换函数，从而拦截调用并写日志（技术参考 Detours [4]、HookAPI [5]、进程注入 [8]、Intercepting System API Calls [10]）。
    2.  **日志大小记录器**：每秒记一次，持续 t；**假设日志受保护、攻击者无法擦除**。
    3.  **关联分析器**：比较 t1→t2 各主机日志大小有无变化，全 0 或全 1 为“相关”，混合为“不相关”；逐时刻累计 CV/UCV，CV>阈值即判可疑。**不考虑变化幅度**（留作未来工作）。
- **机制直观解释**：bot 在指定时间内向 herder 发相近数据、或对外打相近攻击流量 → 高相关；高相关=恶意，低相关=正常。
- **训练方式**：无传统模型训练；阈值由 ROC 实验确定。
- **推理流程**：注入 DLL + 启动记录器 → 收集 t 时间数据 → 分析器打 0/1 累计 CV/UCV → CV 比阈值 → 告警。
- **与已有方法差异**：不分析内容/端口/模式，只看“系统行为同步性”，对加密与非标准端口鲁棒、处理开销低。

## 8. 局限与问题
1.  **环境极小且单一**：4 机、单 bot（sdbot05b）、一人扮三人；难以外推到真实规模与 bot 多样性。
2.  **假设过强**：假设日志受保护、攻击者不能擦日志；现实中高权限 bot 可干扰日志。
3.  **只看变没变、不看幅度**：算法忽略变化量级（作者列为未来工作），既漏掉“低相关恶意”，又把“虚拟机切换”等正常同步误判为相关。
4.  **粒度为群组**：只能检测一组主机协同，无法定位单台被感染主机（未来工作：监控单主机 API 调用数量）。
5.  **仅集中式 C&C**：P2P 僵尸网络未覆盖（更危险、留作未来工作）。
6.  **ROC 评估规模小、表述含混**：误报仅以“1 个/2 个”绝对计数描述，样本极小；"zero true negative" 措辞不严谨，结论统计意义有限。
